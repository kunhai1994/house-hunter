# house-hunter 试用问题清单（2026-05-10）

> 试用场景：「龙岗区，房租 5000 以内，2 房一厅或 1 房一厅，周围有商场。每个小区需要写清建成年份」
> 产出报告：`~/Documents/House-Hunter/深圳市-龙岗区-租房-20260510.md`
> 整体结论：报告**核心字段缺失**（建成年份 + 租金分布），需逐项解决。

## 严重度分级

| 级别 | 含义 |
|------|------|
| **P0** | 阻塞 — 报告失去关键决策能力 |
| **P1** | 高影响 — 数据质量明显错 / 误导用户 |

## P0-1 链家系全网络反爬，候选/挂牌/小区元数据全断

**现象**
- `sz.lianjia.com` PC / Mobile 全 302 → 登录页
- `sz.zu.ke.com`、`sz.ke.com`（贝壳） 同样反爬
- 用 WebFetch 工具走 Anthropic 国外 IP 仍然 302 → 登录
- 房天下、安居客一样（socket 关 / 验证码）

**Root cause**
2026 年中国主流房产站全部上线了「不登录就锁页面」的反爬策略，无 cookie / 非浏览器请求一律拒绝。这不是代码 bug，是数据源能力问题。

**连锁影响**
1. 候选生成 fallback 到百度地图 POI（id 形如 `baidu_map_poi-xxx`）
2. `rental_analyzer.analyze_community()` 输入非数字 id，URL 拼接失败 → `available=False`
3. `community_basic_info()` 无法访问详情页 → built_year/物业/户数/精准坐标全缺
4. 报告"数据来源 → 链家"链接对用户是死链

**已尝试且失败的方向**
- ❌ PC UA + Cookie header 伪装：不够，需要真 session
- ❌ 切 m.lianjia.com 移动端：同样反爬
- ❌ 切贝壳：同样反爬
- ❌ 切房天下/安居客：同样反爬
- ❌ Bing/百度搜索摘要：信息不全或 webfetch 拿到空
- ❌ 百度地图 detail API：字段里没有建成年份等元数据

**可行方向（待你拍板）**
- **A**（最重）：接入用户自己浏览器的真 session（参考 xhs-skills 的 Chrome Extension Bridge 思路）。用户已经登录链家时，扩展把页面内容转发回来。改造量大（~1-2 天工作量）。
- **B**：买商业房产数据 API（详见末尾「数据源采购评估」）
- **C**：放弃链家依赖，承认 skill 在当前网络条件下仅提供「POI 配套 + 小红书口碑」两个维度，文档明示。
- **D**：联系用户已订阅的房产服务（自如、贝壳找房 App API 等）取数据。

## P0-2 租金维度完全失效（rental_score 全 50 中性）

**现象**
本次报告 5 个候选的「租金」一栏全部 50 分，跟用户预算 5000 完全无关联。等于用户没设预算。

**Root cause**
是 P0-1 的直接连锁。`_enrich_one` 看到 id 非链家数字，直接 `rental={"available": False}`，`rental_analyzer.rental_score()` 默认返 50 中性分。

**影响**
用户视角：「我说了预算 5000，报告推荐的小区是不是都在预算内？」—— 报告**无法回答**。

**方案**
绑定 P0-1。链家恢复 → 自动解决。不修 P0-1 这条单独修没意义。

## P1-1 小红书 sentiment 算法误判（粗糙关键词 polarity）

**现象**（来自本次报告）
- Top 1「**万科房子质量真的辣鸡**，还好是租房」 → 归到 👍 亮点
- Top 3「避雷‼️艾特的圈子租房骗子」 → 归到 👎 槽点（其实是吐槽中介，不是吐槽小区）

**Root cause**
`scripts/analyzers/sentiment_aggregator.py:27-29`
```python
POSITIVE_WORDS = ["不错", "推荐", "好", "棒", ...]
NEGATIVE_WORDS = ["差", "踩雷", "坑", "避雷", "吵", ...]
```
简单计数：正面词 > 负面词 → 👍。
- "辣鸡"不在负面词列表 → 算 0 负面
- "还好"被部分匹配为正面 ❓（实际 "还好" 不在列表，但 "好" 在 → 触发匹配）—— **这是个 bug，部分匹配让"还好""不好"都算正面**
- 没识别评价对象（"万科房子质量"是品牌评价，不是小区评价）

**方案**
- **A 短期**：词典严格化 — 全词匹配（用 jieba 分词或 `\b{word}\b` 边界），并把"辣鸡""垃圾""避雷""避坑""踩坑""无语""差评"加入负面词
- **B 中期**：用 LLM 做笔记摘要（已经有 webfetch 抓笔记详情时可以让 LLM 提取「住户对该小区的评价」），但要承担成本
- **C 长期**：训练或调用情感分析模型

我倾向 A + B（B 仅对高互动 Top N 笔记跑，控成本）。

## P1-2 小红书笔记噪音：中介营销帖 / 不相关帖混入

**现象**
- 「珑城原点复试一房 1800 押一付一可停车配套好」 — 这是中介出租广告
- 「避雷‼️艾特的圈子租房骗子」 — 吐槽中介，不是吐槽小区

**Root cause**
`community_reviews()` 只用关键词搜，不过滤帖子类型。中介帖 / 骗局帖关键词命中率最高（标题写小区名最积极）。

**方案**
- **A**：在 sentiment_aggregator 加黑名单关键词过滤（"中介" "押一付一" "联系我" "vx" "电话" "私聊" "出租信息" → 直接 drop）
- **B**：识别作者特征（小红书帐号名含 "租房" "中介" "顾问" "管家" 等 → 降权或 drop）
- **C**：要求笔记必须含居住体验关键词（"住了" "住过" "邻居" "物业" "周末"…）

A + C 是低成本组合，推荐。

## P1-3 POI 显示重复（同一站不同出口都列出）

**现象**
```
- 地铁站（半径 1000m）
  - 龙城 — 207 m
  - 龙城 — 207 m
  - 龙城 — 269 m
  - ...还有 1 家
```
看起来"4 个地铁站"，实际是同一站不同出入口。

**Root cause**
`baidu_map.search_nearby` 返回的 POI 没去重；地铁站每个出口 / 上下行月台都是独立 POI。

**方案**
- 在 `poi_validator` 显示侧按 name 前缀（去掉"-A 口" "B 口" "1 出口"等后缀）聚合，每站只显示最近的一个出入口
- 影响只在 transport.subway / transport.bus_stop 这两类；其他类别（如商场）不需要

改动量小（~半小时）。

# 📦 数据源采购评估（你问的「买现成 POI」）

## 先纠正一个判断：本次试用 **POI 不是瓶颈**

看本次报告 Top 1 的 POI 段：
```
- 世贸百货 — 161 m
- 龙城万科里 — 464 m
- 龙城商场(龙河路店) — 791 m
- ...还有 11 家
```
百度地图返回的距离、命名、品牌识别**都是准的**。瓶颈在**房产数据**（小区元数据 + 挂牌价），不是 POI 数据。

## 真正需要买的是「房产数据」，不是 POI

按本次问题的成因，3 类商业数据源能解决：

### 类别 1：房产挂牌数据 API（解决 P0-1 / P0-2 / P0-3）

| 服务商 | 优点 | 缺点 | 估计成本 |
|-------|------|------|----------|
| **贝壳找房开放平台** | 官方、合规、字段最全（含建成年份/户数/物业/挂牌价） | 需 B 端资质审核，不接受个人 | 月费 ¥5k+，对接周期 1-2 周 |
| **极海数据** | 第三方汇聚多平台数据 | 部分字段更新滞后 1-2 天 | API 包年 ¥3k-¥10k |
| **合合信息（启信宝）** | 含物业公司工商数据 | POI/挂牌价覆盖弱 | 视套餐 |
| **诸葛找房（已退市但数据仍流通）** | 历史数据 | 实时性差 | — |
| **房天下数据中心** | 国内房产数据老牌 | 反爬严，公开 API 少 | 需谈 |

### 类别 2：小区基础数据集（仅建成年份 / 户数 / 物业，不含挂牌价）

| 来源 | 描述 | 估计 |
|------|------|------|
| 自然资源部 / 各市住建局公开数据 | 部分城市有「小区目录」公开数据集（不全） | 免费但残缺 |
| 高德地图 POI 商业版 | 比开放版多元数据字段，包括建成时间 | ~¥8k-¥20k/年（按 QPS 阶梯） |
| 百度地图 POI 商业版 | 同上 | 类似量级 |
| **小区数据爬虫服务（如：店探探/网盾/极光）** | 把链家数据爬好直接卖 | ¥2k-¥5k 起 |

### 类别 3：POI 服务升级（**这次试用并不需要**）

- 高德地图商业版（带品牌库、商圈、客流热度）
- 灵犀（极海）POI 数据集

## 我的建议

**短期（1-2 周内）**：
- 跳过商业采购。先做 P1-1 / P1-2 / P1-3 这些代码层能改的（情感分析、噪音过滤、POI 去重） — 报告质量能提升一个台阶
- 接受租金/建成年份缺失，文档明示限制

**中期（如果项目要正式发布）**：
- 优先评估「贝壳找房开放平台」（合规度最高，字段最全）
- 备选「极海数据」（个人/小团队可拿）
- 月成本预算 ¥3k-¥5k 是合理区间，再低的源数据质量没保障

**长期（如果做大）**：
- 自建「用户浏览器 bridge」方案（类比 xhs-skills），让每个用户用自己已登录的链家账号，转发数据回 skill。
- 这条路在合规上比购买商业 API 微妙（用户视角是"我自己看自己的 app"，平台视角是自动化），但技术上可行。

# 🛡️ 抗反爬抓取服务调研（你问的「类似 Apify 的」）

> 调研时间：2026-05-11
> 调研对象：能否通过第三方抓取/代理服务**让链家系恢复可访问**

## 调研对象分类

### A. 通用爬虫平台（让你写 actor 然后云端跑）

| 服务 | 对中国站点能力 | 上手成本 | 计费 |
|------|--------------|---------|------|
| **[Apify](https://apify.com/actors)** | 没有现成 lianjia actor，但平台支持自定义 Actor + 残留 GitHub 上的 [lianjia-beike-spider](https://github.com/ngwangshu/lianjia-beike-spider)（"**仅供学习参考，请勿用于商业用途**"）| 中 — 需要自己写 actor 或 fork 现成爬虫 | 按 compute units，~$0.25-$2/千次 |
| **Zyte（前 Scrapinghub）** | 通用 | 高 — 偏企业 | $50+/月起 |
| **Crawlbase（前 ProxyCrawl）** | 通用 | 低 | 按请求 |

**结论**：Apify 路径要自己实现 lianjia 爬虫逻辑（GitHub 上有现成代码可改），但要承担两层风险：
1. 链家平台条款（用户协议禁止"通过爬虫/自动化批量获取数据"，存在合规风险）
2. Apify 的 actor 跑在国外，对链家 IP 反爬是劣势

### B. 反爬 API 服务（HTTP 中间层，自动绕过 CAPTCHA / IP 封）

| 服务 | 对**中国**站点 | 起步价 | 中国 IP 池 |
|------|-------------|--------|----------|
| **[Bright Data Web Unlocker](https://brightdata.com/products/web-unlocker)** | 明确有[中国住宅/移动 IP](https://brightdata.com/locations/cn)，Web Unlocker 主打绕 CAPTCHA + IP 封 | ~$500/月起 | ✅ 四种网络（住宅/移动/ISP/数据中心） |
| **[Oxylabs](https://oxylabs.io)**（Bright Data 主要竞争对手） | 类似，有中国 IP 池 | ~$300/月起 | ✅ |
| **[ZenRows](https://www.zenrows.com)** | 主打 Cloudflare/DataDome；中国站点反爬模式不同，未明确验证 | ~$70/月起 | ⚠️ 不确定 |
| **[ScrapingBee](https://www.scrapingbee.com)** | 中等难度站点 84% 成功率；对链家系**没有**公开验证 | ~$50/月起 | ⚠️ 不确定 |
| **[ScraperAPI](https://www.scraperapi.com)** | 实测对 Cloudflare/DataDome 较弱 | ~$50/月起 | ⚠️ 不确定 |

**结论**：Bright Data Web Unlocker + 中国住宅 IP 是**最可能成功**的路径，但月费 $500+ 起，且无对链家系的官方验证（需要自己花 trial 信用测）。其他几家便宜的对中国反爬覆盖不明，风险高。

### C. 纯 IP 代理（要自己写抓取逻辑）

| 服务 | 价格 | 备注 |
|------|------|------|
| **快代理 / 蘑菇代理 / 芝麻代理** | 国内代理 ¥1-¥10/千次 | 便宜，但链家不是只看 IP — 还看 TLS 指纹 + cookie + 行为，单纯换 IP 大概率仍被挡 |
| **Bright Data 中国住宅 IP**（无 Unlocker） | $15+/GB | 同上，单纯换 IP 不够 |

**结论**：单买代理 IP 不解决问题，因为链家不仅看 IP。

### D. 国内合规通道（不绕反爬，是官方授权）

| 服务 | 性质 | 准入门槛 |
|------|------|---------|
| **贝壳找房开放平台**（B 端） | 官方授权 API | 企业资质审核，月费 ¥5k+ |
| **极海数据 / 城市数据团 / 财新数据** | 第三方汇聚数据服务 | B 端订阅，¥3k-¥10k/年 |
| **天眼查 / 启信宝**（房产关联工商数据） | 已开 API | 月费 ¥500-¥2000 |
| **国家政务公开数据**（住建局 / 不动产登记） | 部分免费 | 数据覆盖参差 |

**结论**：合规度最高，但门槛高（需要公司资质），适合产品商业化阶段。

## 法律/合规风险提示

无论走 A 还是 B：
1. **链家用户协议第 X 条**：明确禁止爬虫和自动化批量获取
2. **PIPL（个人信息保护法 2021）**：抓取「房源带房东信息」类数据需额外评估
3. **反不正当竞争法**：批量爬取并对外提供服务有不正当竞争风险（参考"大众点评 vs 百度地图"判例）
4. **你的 skill 当前是个人工具**：自用 + 小范围分享，风险较低；如果对外开放，需法务把关

实际操作上，"个人调研用途+低频"几乎不会被追究，但**不要做的事**：
- 大量并发（>10 QPS 容易触发法律线，不是反爬线）
- 把抓到的数据二次销售
- 把别人的房源信息整合后商业化

按**投入 → 产出**排序：

### 🥇 最务实：**优先做 P1-1/P1-2/P1-3 代码层修复**（0 成本）

### 🥉 中期：**Bright Data Web Unlocker trial 验证**（$500/月）
- 拿 free trial 跑 50-100 个链家详情页，**实际验证成功率**

## 🚫 贝壳开放平台实测结论（2026-05-11）

| 维度 | 结果 |
|------|------|
| AppKey 注册 | ✅ 个人可注册并拿到 AppKey + AppSecret |
| Token 接口 | ✅ `POST https://gw-open.ke.com/oauth/token` 成功，OAuth2 client_credentials |
| 业务 API 调用 | ❌ `/api/assessTransactionCase` 三种参数组合**全部返回** `code:-2001 没有剩余配额` |
| 产品矩阵匹配度 | ❌ 估值/验真/成交（B 端金融），无"小区档案 + 当前挂牌"接口 |
| 普通用户可用性 | ❌ 配额需"申请试用 + 谈商务"，本质是 B2B 合作模式 |

**结论**：即使开发者自己注册了 AppKey，没有商务签约也是空配额，这条路对 house-hunter 完全不可用。详见 plan-lianjia-bridge.md §8.5。
